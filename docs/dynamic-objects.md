# Dynamic object platform - backend foundation

## The one-entity rule

Users design their own object types ("Property Inspection", "Customer Survey", ...). Those designs are
**metadata**, never C# classes and never new database tables:

| Concept | Entity | Table |
| --- | --- | --- |
| A user-created object type | `ObjectDefinition` | `ObjectDefinitions` |
| A field on that type | `FieldDefinition` | `FieldDefinitions` |
| A dropdown / multi-select choice | `FieldOption` | `FieldOptions` |
| **Every actual user record** | `ObjectRecord` | `ObjectRecords` |

`ObjectRecord` is the only entity holding user-entered business data. Its relational columns
(`Title`, `Description`, `OwnerId`, timestamps) are normal columns; the dynamic part is a single
`jsonb` column, `Values`, keyed by `FieldDefinition.Key`.

Record JSON stores **values only** - never labels, types, validation settings or display order. Those
live in `FieldDefinitions` / `FieldOptions`, so a label can be reworded without touching a single record.

## Storage decisions

- **IDs**: `long` in C#, `bigint generated by default as identity` in PostgreSQL. No GUIDs, no public UUID.
- **Dynamic values**: `jsonb`, one object per record, guarded by a check constraint
  `jsonb_typeof("Values") = 'object'` and defaulting to `{}`.
- **Field settings**: `jsonb` too (`CK_FieldDefinitions_Settings_IsObject`), so new per-type settings
  never need a new nullable column.
- **JSON CLR type**: `JsonDocument`. Npgsql maps it to `jsonb` natively with a value comparer, and it
  keeps the exact JSON shape (a `Dictionary<string, object>` would erase number/string/bool distinctions
  at runtime and make "do not coerce types" impossible to enforce).
- **`FieldType`** is persisted as text (`character varying(32)`) so the tables stay readable in psql.
- **Timestamps** are UTC `DateTime`, stored as `timestamp with time zone`.

### Delete behaviour

| Relationship | Behaviour | Why |
| --- | --- | --- |
| `ObjectDefinition` → `FieldDefinition` | Cascade | Only reachable when the definition itself is deleted, which requires it to have no records. |
| `FieldDefinition` → `FieldOption` | Cascade | Options are meaningless without their field. |
| `ObjectDefinition` → `ObjectRecord` | **Restrict** | User data must never disappear because metadata was deleted. |

Prefer flipping `IsActive` to `false` over deleting anything once data exists.

### Indexes

`ObjectDefinitions(OwnerId)`, `ObjectDefinitions(OwnerId, Name)` unique, `FieldDefinitions(ObjectDefinitionId)`,
`FieldDefinitions(ObjectDefinitionId, Key)` unique, `FieldOptions(FieldDefinitionId)`,
`FieldOptions(FieldDefinitionId, Value)` unique, `ObjectRecords(ObjectDefinitionId)`,
`ObjectRecords(OwnerId)`, `ObjectRecords(CreatedDate)`.

No GIN or JSON expression indexes yet: nothing currently queries *inside* `Values`. Add them when a real
query pattern appears (filtering or reporting on a specific key), not before.

## Validation

`Validation/RecordValueValidator` is the only door into `ObjectRecord.Values`. It loads the **active**
fields and **active** options of the definition, then checks:

1. `Values` is a JSON object.
2. No unknown field keys.
3. Every required field is present and non-null (a required text field also rejects whitespace-only;
   a required multi-select rejects `[]`).
4. Optional fields may be missing or explicitly `null`.
5. The JSON type matches the field type - **never coerced**. `"8"` for a numeric field is an error.
6. Settings are applied: `minimumLength`, `maximumLength`, `minimum`, `maximum`, `step`,
   `minimumDate`, `maximumDate`, `minimumDateTime`, `maximumDateTime`, `minimumItems`, `maximumItems`.
7. Dropdown values must be an active option value.
8. Every multi-select entry must be an active option value, with no duplicates.

Expected JSON representations:

| Field type | JSON |
| --- | --- |
| `Text`, `LongText` | string |
| `Integer` | number with no fractional part |
| `Decimal`, `Range` | number |
| `Boolean` | `true` / `false` |
| `Date` | `"YYYY-MM-DD"` |
| `DateTime` | ISO 8601, preferably UTC (`2026-08-22T04:30:00Z`) |
| `Dropdown` | string holding a `FieldOption.Value` |
| `MultiSelect` | array of `FieldOption.Value` strings |

Errors are returned as `{ fieldKey, errorCode, message }`. `errorCode` is a stable slug
(`required`, `invalid_type`, `unknown_option`, ...) that mobile clients can switch on without parsing English.

## Versioning: what is safe to change

No versioning subsystem exists yet, and there is deliberately **no version number** on `ObjectDefinition` -
a number would imply old schema snapshots are preserved, and they are not.

**Safe at any time** (existing records stay valid):

- Renaming `FieldDefinition.Name`, editing `Description`, changing `DisplayOrder`.
- Renaming `FieldOption.Label`.
- Adding a new optional field.
- Adding a new option.
- Deactivating a field (`IsActive = false`) - old records keep the data, and the key is simply no longer accepted.
- Widening a constraint (raising `maximumLength`, lowering `minimum`).

**Requires a data migration** (existing records may become invalid or unreadable):

- Changing `FieldDefinition.Key` - the key *is* the JSON property name; renaming it orphans every stored value.
- Changing `FieldOption.Value` - the value *is* what is stored in record JSON.
- Changing `FieldType`.
- Making an existing optional field required.
- Narrowing a constraint (lowering `maximumLength`, raising `minimum`, changing `step`).
- Deleting a field or an option that records already reference (deactivate instead).

That is why keys and option values are stable identifiers and labels are not.

**How versioning could be added later**, without changing the storage model: add a
`ObjectDefinitionVersion` table holding a full JSON snapshot of the fields and options as they were at
publish time, plus a `DefinitionVersionId` column on `ObjectRecord` pointing at the snapshot each record
was written against. Validation would then load the snapshot for old records and the current definition
for new ones. Nothing in the current schema blocks that.

## Ownership

`OwnerId` is never read from a request body. Today it is resolved from an `X-Owner-Id` header in
`Security/CurrentOwner`; when authentication lands, that one file changes to read the authenticated
principal, and every endpoint keeps working. Every query is filtered by owner.

## Deliberately not built yet

Frontend, charts, dashboards, AI chat, file/image/signature fields, record-to-record references,
calculated fields, workflow automation, complex permissions, definition version history, analytics
projections, and soft-delete infrastructure.
